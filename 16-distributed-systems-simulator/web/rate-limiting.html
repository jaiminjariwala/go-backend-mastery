Why rate limiting?

I protect a service from excessive traffic and put a bound on how quickly work is admitted. Load balancing chooses where a request goes; rate limiting decides whether it may enter at all. A rate limiter does not add server capacity or guarantee that allowed traffic is safe for every server.

The ticket-guard analogy

A guard has five admission tokens. Each person uses one. Tokens regenerate at two per second, up to five. Once there is less than one token, the guard refuses entry for now. Nobody waits in a queue in this experiment.

Capacity versus refill rate

Capacity is the maximum saved tokens and permits a short burst. Refill rate is the number added each second. With capacity 5 and refill 2/second, five requests can pass immediately if the bucket is full, followed by roughly two per second over time. This is not a strict limit of two in every one-second window.

Fractional tokens

The bucket refills continuously in simulated time. At two tokens per second, 100 ms adds 0.2 tokens. A request still needs one whole token. The history shows refill since the previous arrival, capped by bucket capacity. Step advances to the next arrival; it also applies the refill earned during the intervening time.

What does 429 mean?

HTTP 429 means Too Many Requests. A rejected request consumes no token and never reaches the server. Retry after is the modeled minimum wait for one token if no other request consumes it first, not a reservation or automatic retry. A real Retry-After header uses whole seconds or an HTTP date; this history displays milliseconds for teaching.

One shared bucket, not one per person

Every person competes for the same API-wide bucket. A per-user or per-IP limit would use separate buckets keyed by identity. Multiple application instances need coordinated state, often using atomic operations in a shared store such as Redis, to enforce a shared limit correctly.

What is simulated?

The Go API calculates token decisions. The 200 and 429 entries describe modeled responses; the simulation endpoint itself returns the complete history as JSON. No production endpoint is protected by this demo, and no real traffic or Redis is used. Every run starts with a full bucket. Playback speed and moving lines are illustrations, not network latency measurements.
