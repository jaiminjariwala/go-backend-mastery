Where do overlapping requests wait?

In this model they do not wait in a queue. Server A can process request #1 from 0 to 500 ms and request #3 from 200 to 700 ms concurrently. Both are active between 200 and 500 ms. Go keeps their scheduled completion records in memory. A real server has finite resources, and requests may wait for CPU, a database connection, or a configured queue. A load balancer does not automatically create one queue per server.

Why are there twice as many events?

An event is a recorded occurrence, not a new request. Each successful request produces two events: routed and completed. 100 successful requests produce 200 events. Rejected requests produce only one event because they never reach a server.

Users and timing

100 users means 100 requests, one per person. I see the exact number of cartoons up to four; larger groups use four representative cartoons. ms means milliseconds: 1000 ms = 1 second. With 100 ms between arrivals, requests arrive at 0, 100, 200 ms, and so on.

Step and simulated time

Step advances one event: a request arrives or a server finishes it. The history table shows when each event happens in the model, not how long I have watched. Two events can share the same time. Run experiment starts automatic playback. Step stops automatic playback and advances one event; Reset clears the results.

Server settings

The minus and plus buttons remove or add a simulated server, between 1 and 30. All servers are healthy. Service time is how long one request takes to finish. Make one server slower gives server 1 four times the normal service time. Round robin still takes turns; least connections can send fewer new requests to the slow server because its requests remain active longer.

Assigned, active, and done

Assigned is every request sent to that server so far. Active is requests still being worked on. Done is finished requests. Example: assigned 10, active 3, done 7. Assigned = active + done.

The receptionist analogy

A receptionist sends visitors to service counters. Round robin takes turns. Least connections looks at how many visitors each counter is still serving.

What should I notice?

Round robin distributes arrivals, not work duration. A slow server can accumulate more active requests even when its total assigned count is similar.

Not a performance benchmark

These are simulated users and server instances. Playback speed is for learning; the displayed milliseconds are modeled time, not real measured latency. No actual tickets are sold. Requests run independently with fixed service times, without a capacity limit or queue. Server health stays fixed during each experiment. The moving lines illustrate the selected route, not measured network travel time.
